## 上线前需修复

### P1：旧模块撤权后仍可用，已隔离复现

位置：`server/middleware/jwt-auth.js:15`、`:29`、`:38`。

JWT 验证仅重新检查账户状态/密码版本，之后把令牌旧权限放到 req.user；requirePermission/requireAnyPermission 使用旧权限。隔离复现：登录带 business 权限 → 撤销 business → 数据库权限为 false，但同令牌访问受保护路由仍返回200。固定15天登录会延长此问题影响窗口。

修复建议：鉴权时读取当前用户角色与权限，并保留令牌会话签名字段供截止时间校验；回归各业务模块、撤权、管理员角色改变、密码重置、15天边界。标准和反馈模块已有 currentUser 实时检查，不应误报它们同样存在该漏洞。

### P1：完整群公告仍为纯文本，未完成属性表格需求

位置：`server/services/standard-notify.js:81`。

审核通过后仍调用 sendWecomText。现有表格图片是预览，不是实际群发布路径。需要接入可发送的完整属性表格，并保留独立 @所有人、长内容和发送状态验证。不得把截图预览当成已落地。

管理员直接保存的创建/更新路由未调用群发布通知。这是当前明确行为；若业务口径要求“任何正式发布都进群”，也需要统一此路径。

### P1：生产依赖有已知漏洞，需修复或完成可达性评估

`npm audit --omit=dev --registry=https://registry.npmjs.org` 实时结果：

- 根项目3个受影响包条目：xlsx（高，实际0.18.5）、fflate（中，0.8.2）、dompurify（低，3.4.13）。
- server 6个受影响包条目：proxy-addr（严重）、express/body-parser/qs/node-cron/uuid（中；包含传递依赖，不能简单等同独立漏洞数量）。
- xlsx 的原型污染、ReDoS 与读取工作簿有关；现有导入校验、Worker和ZIP限制不能替代修补底层解析器。npm audit 报告 xlsx 无可用 npm 自动修复，不应执行强制升级了事。
- proxy-addr 的公告要求特定信任代理配置；当前 server.js 未启用 trust proxy，尚未证明该严重漏洞在当前入口可利用。需要升级可修复依赖，并确认实际部署配置。
- 升级 node-cron 可能跨主版本，需要回归生产日报和标准提醒，不可直接 npm audit fix --force。

原始报告：`prelaunch-20261019-root-audit.json`、`prelaunch-20261019-server-audit.json`。

## 上线环境与数据门槛

1. 线上 Nginx 请求体限制未核实。部署脚本只追加 /api/ 代理，未设置 client_max_body_size。反馈支持3张、每张2MB图片，JSON base64后约8MB；Express为20mb，但Nginx默认1m会先返回413。应核对实际站点配置并用真实反向代理验收多图提交，不能只测Express直连。
2. 发布流程先部署静态文件再部署API，有新旧不兼容窗口；未见自动一致性备份和回滚切换。上线前保存对应前后端版本包，备份 users、各SQLite业务库及新 feedback.db（如已有），采用SQLite一致性备份，安排维护窗口并做恢复验证。
3. 仅使用正式源文件受控导入，不整体同步本地 data。若线上已有旧70套卫浴配对标准，需要核对来源、先预览，再事务停用并保留历史；本地临时替换脚本不等同已有可审阅的正式迁移入口。
4. 定时提醒启动时立即扫描；本地当前2条待审均超过2小时，均有激活且已绑定企微的审核人。重启启用真实 webhook 后可能立即向群催审。先确认正式群/测试群、旧待审任务名单及真实用户的企微绑定。
5. 金蝶 SP0201-A 的分类修正需在实际金蝶数据及线上接口重新验收；本轮没有调用生产金蝶，不把旧记录当成当前验证。
6. 群公告送达结果没有持久化 outbox 和受控补发入口。重启可能丢失发送进度；不能再次审核来补发。若先小范围试用，必须明确人工核查及补发流程；要求自动可靠必达时应先补此能力。
