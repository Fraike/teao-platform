# 产品标准与表格改动复盘（2026-10-14）

## 结论

当前 760 条标准的使用规模，可继续沿用 React、Express 和 SQLite。下一阶段的重点是避免每次请求、每次交互处理全部数据，同时保持发布版本、编辑草稿与审批权限隔离。

这次改动解决了用户可见的重复滚动条、中文输入阻塞、行选择整表重绘及侧栏连续宽度重排。仍有两个已复现的上线／编辑风险及两组由代码确认的日报一致性问题，应先处理。不能把下列所有问题归因于本次改动；没有逐项进行历史引入点定位。

范围：产品标准审核、发布、查看、Excel 主表导入，共享表格／框架、装配和注塑生产日报。智能卫浴仍不在本期导入范围。只审查代码、只读本地数据库统计、在临时数据库和隔离浏览器中验证，未修改应用代码或实际业务数据。

## 本次已有的有效改进

- 审核绑定版本和 revision；后端查询最新用户权限，限制自审；修订期间旧发布版本仍供普通用户查看。
- Excel 预览与确认绑定内容、操作者、数据库状态及有效期，确认前备份、复查权限，事务写入。
- 分类、项目变体和原始批注保留；此前 Excel 对账证明主表 760 行、10,652 项字段一致，原文批注 1,194 个精确归档。该结论是历史对账结果，本轮未重跑全部源文件审计。
- 中文输入期间不提交中间搜索，搜索防抖、下拉节点保持稳定；异步刷新请求序号防止旧响应覆盖。
- 标准行选择通过行级订阅，只更新旧／新选中行；内容按记录缓存，权限变化仍刷新操作列。
- 表格宽度适配不再由共享组件 React 状态反复驱动；侧栏尺寸即时切换，表格视口高度按实际空间分配。
- 标准及日报关闭额外滚动控件，保留内部横向滚动和原有吸顶表头；日报已有日期筛选、按日期加载、每组 50 行展示及数据库索引。

## 当前规模与隔离量测

本轮只读统计：760 条标准、760 个版本、1,194 条原文批注、1,730 条变更记录。

模拟条件：本机 Node 24、隔离 SQLite WAL；每条标准包含历史／发布／工作共三个版本（列表读取其中两个非归档版本），六种分类、十个文本字段；10% 的工作版本为待审核。各查询预热一次、重复五次取中位数。没有并发、网络、浏览器渲染或压缩；不能作为生产服务器延迟保证。

- 1,000 条标准／3,000 个版本：全量查询 7.9ms；待审核查询 6.9ms；单分类查询 6.8ms；JSON 序列化 0.9ms；全量未压缩响应 1.17MiB。
- 10,000 条标准／30,000 个版本：全量查询 111.8ms；待审核查询 105.3ms；单分类查询 107.5ms；JSON 序列化 9.1ms；全量未压缩响应 11.68MiB。
- 50,000 条标准／150,000 个版本：全量查询 612.4ms；待审核查询 585.2ms；单分类查询 573.3ms；JSON 序列化 51ms；全量未压缩响应 58.48MiB。

这些查询使用当前 listStandards 实现。只查待审核或单分类仍需扫描并组织全量数据。50,000 条时同步服务函数约 0.6 秒，可能阻塞同一 Node 进程上的其他请求。查询计划确认非归档版本查询全表扫描并使用临时排序；按 standard_id 取最新版本虽然使用索引，仍需额外排序。

本轮重新运行 test:standards，相关回归通过。浏览器在临时数据下复现表单重置；临时数据库复现作废记录导入为 published。未执行生产环境压力测试。

## 先修正确性：上线或日常使用前处理

### 1. 标准表单自动刷新覆盖未保存输入（P1，已复现）

来源：src/components/standard/StandardFormModal.tsx:65、src/pages/ProductStandardPage.tsx:106。

初始化 effect 依赖 categories，focus 刷新替换分类数组后再次 resetFields。浏览器验证：新增表单输入“未保存的客户名”，触发恢复焦点刷新后变为空字符串。

方案：按一次打开会话／编辑对象初始化；模板刷新不得重置 dirty 表单。切换分类需要明确字段保留规则。验收：切换窗口、手动刷新、分类更新均不丢输入；切换编辑对象正常初始化；保存仍校验当前 revision。

### 2. 原 Excel 的作废行在新环境初始化时仍会发布（P1，已复现）

来源：src/lib/standardImport.ts:148、server/services/standard-store.js:858。

解析只警告，确认导入统一写 published。临时库验证：备注“此行作废，放筒型阻尼器行内”仍成为已发布。本地已经停用 SP0103-A，不代表从原 Excel 重新初始化的服务器会自动停用。

方案：将已确认分类、项目变体、停用决定记录为可复跑的数据迁移清单，绑定来源哈希与完整项目身份，不只按可重复序号匹配。已确认的作废项导入为停用；其他含作废的歧义项要求人工确认并阻止直接发布。验收：全新临时库从上线源文件导入、应用迁移、再对账，发布／停用数量和原文批注都符合清单；重复运行不新增或复活停用项。不要全量覆盖线上新增审核数据。

### 3. 装配日报保存后指标和汇总不一致（P2，代码确认，未浏览器复现）

来源：src/pages/ProductionEntryPage.tsx:200。

保存只回写输入字段，忽略完整响应，未刷新达成率、合格率、PPM及日期汇总。注塑已有回写完整响应、重算单组汇总的可参考实现。

方案：回写权威记录，重算受影响日期，保留其他分组引用，不重新下载所有日报。验收：修改当日数量／不良数后行指标和日汇总立即与服务端一致。

### 4. 日报历史迟到响应和陈旧缓存（P2，代码确认，未浏览器复现）

来源：src/pages/ProductionEntryPage.tsx:221、src/pages/ProductionEntryInjectionPage.tsx:304。

先查 A 再打开 B，A 迟到响应仍可写入当前抽屉；他人更新后，普通刷新没有清除历史缓存。注塑缓存命中也未统一重置 loading。

方案：历史会话使用请求序号或取消控制器；打开／关闭重置状态；缓存带 TTL、容量上限，写入和手动刷新失效。验收：乱序响应不串记录，更新后能查到新历史。

## 按效率排序的后续优化

### 第一批：后端分页、筛选及轻量通知（最优先）

来源：server/services/standard-store.js:445、src/pages/ProductStandardPage.tsx:103、server/services/notifications.js:13、src/components/NotificationBell.tsx:31。

- 列表 API 增加 page/pageSize，服务端接收分类、状态、性质、客户、型号、料号及项目筛选。SQL 先确定每项“可见发布版或工作版”，再筛选和分页，不能简单取最新版本而泄漏草稿。返回 total 和当页 rows，列表不带历史／批注。
- 通知专用 SQL 只查询 pending_review、排除当前提交人，返回未处理总数及最多一页明细，避免通知轮询再次组装全量标准。
- 根据新 SQL 的查询计划补复合索引，例如 standard_id + version_no、状态／提交人相关索引；已存在的单字段索引无需重复增加。不要先盲目堆索引。
- 前端 200 行分页目前只限制 DOM，不限制下载和内存。分页下推后，可默认 50～100 行并保留需要时的选择；分页状态与筛选变化一致重置。
- 首先保留中文输入隔离、防抖和旧响应保护；新增 AbortController／并发去重，让被覆盖的请求不继续浪费下载。
- 模糊匹配 %关键词% 不会自动受普通 B-tree 加速。规模继续增大时按真实搜索形式选择前缀、规范化搜索列或全文检索，不能承诺仅加索引即可加速任意中文子串搜索。

### 第二批：减少重复请求与日报计算

- 分类模板复用缓存；普通恢复焦点先判断数据新鲜度，优先 ETag／版本戳条件请求。保存、提交、审核、停用成功后按受影响标准／查询范围失效，手动刷新保持强制刷新能力。
- 缓存按用户会话和权限可见范围隔离，退出／撤权时清除。普通用户不能复用工程部包含草稿的缓存。通知关闭后台轮询，恢复可见后立即轻量检查；多用户同时请求可短时合并。
- 日报日期卡片 memo，排序结果按记录引用和排序方向缓存；直接 rowKey=id，不为每条记录复制 key 对象。单元格更新只改变所属日期。持续“加载更多”需要控制日期卡片数量。
- 日报当前按日期分页，不等于行级分页：单日大量记录仍一次下载全部。大数据时区分日期汇总查询与分组明细分页，避免行分页改变汇总口径；长期日期导航考虑游标，保留全日权威汇总。
- 详情主数据、版本历史、变更、原文批注拆分按需接口；历史和批注分页，抽屉打开后仅获取必要内容。

### 第三批：导入和可观测性

- Excel 同步解析放 Worker；限制解压后实际行／列／单元格量，不只限制 10MB 文件大小。批注先按行建 Map，替换每行 filter 所有批注的 O(行数 × 批注数) 扫描。
- 保留预览—确认—备份—事务安全链路；批量导入复用 prepared statements，避免每条记录／批注重复 prepare 及 latestVersion 查询。超过现有 10,000 条上限后再设计后台导入任务与失败恢复；当前不应直接放开上限。
- 导入记录来源文件哈希、工作表、批次、原始单元格、确认决策；维护备份保留周期，防止每次初始化备份长期累积。
- 标准／通知接口加入已有 request-metrics，记录延迟、行数和响应字节数；观测 event-loop 延迟、数据库体积、错误和浏览器输入到下一帧时间。建议验收目标：代表性环境列表 p95 <300ms、行选择可见响应 <50ms、默认页原始响应 <500KB；这些是设计目标，当前没有生产 p95 数据。
- 企业微信目前失败只记日志。若提醒必须可靠，增加本地持久化发送记录、失败重试和幂等键，并显示状态；审核事务成功不应被外部网络失败回滚。暂不需要独立消息队列基础设施。

## 规模增长实施顺序

1. 现在：先修表单丢输入、上线作废导入、日报指标及历史一致性。
2. 下一轮：标准 SQL 筛选／分页 + 轻量通知 + 分类缓存／条件刷新 + 指标采集，建立代表性数据和并发基线。
3. 数千到万级标准、或监测超出预算：检查传输量、SQL计划及日期组大小；落地明细分页、缓存失效、导入 Worker。
4. 数据库大并不自动要求换库。只有出现多服务实例写入、锁等待、持续高写入并发或单机可靠性要求，再评估数据库迁移和后台任务；先验证 SQLite 的索引、查询与事务边界。
5. 表格虚拟化放在受控分页之后。当前标准行订阅已解决点击长任务；虚拟化需要额外验证行高、固定列、键盘高亮和滚动同步，不能作为所有问题的默认答案。
