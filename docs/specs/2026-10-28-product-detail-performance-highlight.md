# 商品详情返回性能与来源行高亮

## 核查结果
详情路由重挂载时清空档案/金蝶详情并重新请求，内部料号入口需要先resolve再请求详情；图纸面板重新请求PDF并销毁/新建PDF.js任务。focus与visibilitychange独立触发刷新，缺少防重复及新鲜度保护。标准列表已恢复滚动锚点，但StandardRowSelectionProvider重新创建时未恢复高亮ID。以上为静态代码确认的重复工作，实际耗时分布待浏览器记录验证。

## 拟实施任务（等待确认）
1. 用真实浏览器记录详情返回请求数和阶段耗时，区分档案加载、PDF下载和PDF解析/渲染，针对实测瓶颈优化。
2. 详情档案/金蝶资料按登录用户与权限、商品ID短期复用；合并同商品并发加载，focus/visibility刷新去重并设置30秒新鲜度。再次进入先显示已有基础资料，后台核对图纸有效性；上传/发布/停用后强制失效和刷新。保留最新的standardId/returnTo上下文，切换客户不得串图。
3. 在已核对有效的同一图纸范围内复用PDF文件资源，限制缓存数量/体积，及时释放；不能仅凭旧缓存继续展示已停用/已失去权限的图纸。打印/下载仍走当前有效性验证。
4. 标准列表快照独立记录最后点击来源标准ID；恢复后默认淡蓝高亮整行（含固定列），持续至手动选择其他行或筛选/分类切换。高亮与滚动锚点分离，滚轮/键盘取消自动定位不清除来源高亮。多客户同料号只高亮来源标准；记录已消失则不高亮其他行。沿用已有单行选择机制，不引入全表逐帧重渲染。
5. 验证三种返回入口、重复切换请求数、后台更新/权限变化/停用、客户范围隔离、PDF资源回收、来源行高亮及筛选变化；完成回归、lint、类型检查、构建和独立复查。

不改全站路由为页面常驻，不提交/推送/部署/重启，不修改现有业务数据。

## 补充：商品详情返回产品标准同样卡顿的实测
只读统计本地标准库：gear_damper约346个有published/draft/pending_review版本的标准，分类7个参数字段。真实Chromium用同等规模模拟数据和即时API返回，产品标准返回首帧约640.8ms；346行、5190个td、约16932个DOM节点。React Profiler记录mount约252ms、布局相关nested update约87ms、随后update约121ms。返回前后完整标准列表请求保持1次，证实没有重复拉列表仍可复现前端停顿；这是开发环境模拟测量，不代表用户真实接口耗时。

原因：当前快照缓存数据和滚动位置，路由切换仍卸载/新建整张非虚拟表格；布局测量和图纸状态回填又产生后续更新。useStandardDrawingStatus每次挂载从空状态重新按150条串行查询，且serialNo列shouldCellUpdate恒true，图纸状态更新会重渲染该列所有行。

后续方案需增加列表渲染层优化：优先评估保留全部记录可浏览的虚拟滚动，减少不可见行DOM，并兼容动态行高/固定列/滚动锚点；缓存与合并图纸状态请求，避免返回后二次整列更新。不能只靠商品详情缓存解决这条返回路径。保留之前的来源标准ID高亮需求。尚未修改实现代码。
