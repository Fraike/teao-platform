# 生产日报恢复执行清单（待单独批准）

执行顺序：**先恢复线上生产日报，再部署新功能**。准备阶段只读核查；代码提交、推送、线上恢复和部署各需单独确认。恢复窗口需要暂停旧版 `teao-api`，期间后台 API 暂不可用，不能在恢复后重新开放旧版无权限限制的导入接口。

1. 上线前完成本地测试、代码审查，按各自确认完成提交与推送。GitHub 的部署工作流是手动触发；推送本身不得触发部署。预先备好恢复工具和新版本，但不部署新功能。
2. 先只读核对线上两表条数、最后日期、记录 ID 范围、`audit_log` 最后 ID、两张日报全表 SHA-256 指纹和 `PRAGMA quick_check`。10 月 12 日覆盖导入的原始基线为装配 2,808 条、注塑 3,711 条、审计末尾 19,794；之后已有新的注塑 INSERT，必须单独核对这些审计与当前记录完全一致。若出现 INSERT 以外的操作、审计缺失或 ID 冲突，停止并重新设计恢复，不能覆盖新写入。
3. 获得单独的**线上数据恢复确认**后，进入维护窗口，停止旧版 `teao-api` 并确认已停止；此时不部署新功能。再次核对记录、审计和指纹。使用 SQLite 在线备份 API 保存原始数据库一致性快照（含已提交 WAL），校验备份并记录路径与摘要。保留原始 DB、WAL 和审计记录，不用普通文件复制替代在线备份。
4. 在隔离环境运行 `server/scripts/preview-production-recovery.js <备份数据库> <新的演练副本路径> <装配整表SHA256> <注塑整表SHA256> <导入后新增注塑记录数> <注塑最新日期>`。脚本只恢复新副本，不修改源库；会验证基线、全表指纹和审计范围，并输出恢复后逐日条数、产量和不良数。预期装配 3,090 条、注塑 4,037 条加经过审计逐条确认的新增记录。人工抽检典型记录及历史；对比其他业务表摘要。原审计回放终点为装配 13,275、注塑 13,218；13,276—19,794 为两次覆盖导入审计，不得混进原状态。
5. 演练全部通过后，执行 `server/scripts/apply-production-recovery.js <线上数据库> <刚生成的已验证备份> <备份文件SHA256> <装配整表SHA256> <注塑整表SHA256> <导入后新增注塑记录数> <注塑最新日期> --apply`。脚本要求 `teao-api` 为 inactive，线上数据库与备份的每张业务表逐行一致，且日报、审计、条数与指纹均符合预期；在单个事务中恢复两张日报并追加已核对的新记录，失败回滚。保留原审计并记录 `RESTORE` 操作。此时旧版 API 仍保持停止，避免未受限的旧导入功能再次覆盖数据。
6. 获得单独的**部署确认**后，触发新版本部署。验证新 API 启动、恢复后的查询/汇总/历史、用户与报价数据未变化，以及普通用户无导入权限；再开放服务。如部署失败，维持写入冻结并报告，不直接重启可任意覆盖导入的旧版 API。

新版本中的 `PRODUCTION_RECOVERY_READ_ONLY` 是额外保险；在本顺序里不能依赖它来冻结旧版服务，因为旧版尚无此代码。本清单不是执行授权，也不包含服务器凭据。
